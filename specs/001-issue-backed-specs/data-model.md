# Data Model: Issue-Backed Specs

## Spec Authoring Field Set (form input)
| Field | Type | Required | Notes |
|---|---|---|---|
| spec_type | enum: feature, bug, documentation | yes | radio |
| spec_title | string, single line | yes | issue title and PR title |
| story | string, single line | yes | "As a ____, I can ____" |
| proposed_solution | text, 10 rows | yes | |
| scope_boundaries | text, 5 rows | no | |
| dependencies | text, 5 rows | no | |
| additional_context | text, 5 rows | no | |
| acceptance_criteria | text, 5 rows | yes | default `- [ ] ...`; must be edited |

## Spec Tracking Issue (GitHub)
- Fields: `issueUrl`, `issueNumber`, title = `spec_title`, body = rendered fields, labels = `spec`, spec type, creator = requester.
- State: `open` at creation. Transition to `closed` only by a human (never automated).
- Cardinality: one issue per spec submission; a submission has many PRs.

## Feature Spec Record
- Generated by `/speckit-specify <issueUrl>`; references the issue URL. Stored in `specs/<dir>/spec.md`.

## Linked Pull Request
- Body contains `Refs #<issueNumber>` (no closing keywords) when a valid number exists.

## Issue body layout
Headings, in order: Story, Type, Proposed solution, Acceptance criteria, then Scope boundaries, Dependencies and Additional context (each only when provided).
